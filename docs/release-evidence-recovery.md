# 릴리스 근거 누락 복구 규칙

GitHub 소스 공개, 앱 사용자 배포, 변경 설명 게시를 별개의 사건으로 확인합니다.
태그, RC 빌드, QA 승인, PR 병합만으로 사용자 배포나 기능 활성화를 확정하지 않습니다.
이 규칙은 브라우저별 조사에 공통으로 적용합니다. 자동 일정 검증은 현재 Firefox iOS에 구현돼 있습니다.
다른 제품은 제품별 공식 출처와 검증기를 마련하기 전까지 같은 예외를 자동 적용하지 않습니다.

## 판정 순서

1. 제품·플랫폼·채널·버전을 식별합니다. 이름이 비슷한 제품과 Desktop·Android·iOS 자료를 혼합하지 않습니다.
2. 공식 릴리스 노트와 버전별 저장소 기록을 확인합니다. 원문과 수집 마감의 리비전을 검증합니다.
3. 승인된 앱 스토어 이력 등 공식 대체 출처에서 같은 버전의 게시 시각과 변경 설명을 확인합니다.
4. 변경 설명이 없으면 공식 배포 일정을 확인합니다. 아래 조건을 모두 만족할 때만 배포 예정으로 분리합니다.
5. 기능·일반 수정·내부 작업을 항목별로 판정합니다. 구체적인 변화가 없는 배포 선언은 변경 설명을 대신하지 않습니다.

| 확인 결과 | 처리 | 완료에 미치는 영향 |
|---|---|---|
| 실제 배포와 버전별 변경 설명 확인 | 변경 항목 분류 | 전체 항목 판정 후 완료 가능 |
| 실제 배포 확인, 변경 설명 없음 | 근거 누락으로 재조사 | 미완료 유지 |
| 검증된 공식 예정 시각이 마감 이후 | 배포 예정으로 별도 기록 | 해당 마감의 필수 변경 분류에서 제외 |
| 예정 시각 도달, 배포나 설명 미확인 | 배포 상태 미확인으로 재조사 | 미완료 유지 |
| 일정 충돌·모호한 날짜·출처 오류 | 미확인으로 기록 | 예외 적용 금지 |
| 조회 시작 전의 날짜 미확인 과거 배포 | 과거 미해결 목록 유지 | Firefox iOS 일일 수집만 비차단. 주간·수동 대조는 차단 |

배포 예정은 기능 0건이나 해당 버전의 조사 완료를 의미하지 않습니다.
현재 마감에 필요한 자료를 모두 판정해야 브라우저 전체를 완료할 수 있습니다.
단계적 배포가 시작되면 수집 대상입니다. 100% 배포가 될 때까지 조사를 미루지 않습니다.

## 배포 예정 예외의 필수 조건

- 공식 일정이 정확한 제품·버전과 시각·시간대를 명시해야 합니다.
- 일정의 게시·수정 시각이 수집 마감 이전이어야 합니다. 마감 후의 설명으로 과거 판정을 만들지 않습니다.
- 실제 배포 근거를 먼저 확인합니다. 릴리스 노트나 앱 스토어의 실제 게시가 일정과 다르면 실제 근거를 우선합니다.
- 출처 조회 실패를 미배포로 해석하지 않습니다. 앱 스토어를 검증하지 못하면 일정만으로 누락을 해소하지 않습니다.
- 예정 시각은 마감보다 뒤여야 합니다. 같은 시각도 예외가 만료된 것으로 봅니다.
- 일정의 수정·취소·충돌을 확인합니다. 더 최근의 모호한 안내가 있으면 과거의 유리한 일정으로 돌아가지 않습니다.
- 버전, 예정 시각, 재확인 시각, 고정 리비전 URL, 게시 시각, 인용문, 원문 해시와 관측 시각을 비공개 작업 파일에 보존합니다.

## Firefox iOS 자동 확인

승인된 제품은 Firefox for iOS이며 App Store는 미국 앱 ID `989804926`, 개발자는 Mozilla입니다.
Mozilla 노트가 없고 검증된 App Store 기록에도 해당 버전이 없을 때만 일정을 조회합니다.
마감 이전에 게시된 더 높은 버전이 App Store에 있으면 해당 버전의 미래 일정 예외를 적용하지 않습니다.

[Mozilla 채널 회의록](https://wiki.mozilla.org/Firefox/Channels/Meetings)의 최근 두 목요일 문서를 조회합니다.
MediaWiki API에서 각 문서의 마감 이전 최신 리비전 한 개를 고정합니다.
`Schedule Update`의 정확한 Firefox iOS 버전과 UTC 배포 시각을 검증합니다.
현재 지원 문형은 `Firefox iOS <version> scheduled to start phased rollout at <HH:MM> UTC on <YYYY-MM-DD>`입니다.
예정 시각은 해당 리비전 게시 후 14일 이내여야 합니다. 문형이나 공식 출처 구조가 달라지면 자동 추정하지 않습니다.
새 문형은 원문 확인과 회귀 테스트를 거친 뒤 지원합니다.

`firefox_ios_inventory.scheduled_versions`에 예정 근거를 기록합니다.
`schedule_errors`에는 일정 검증 실패 이유를 남깁니다. 기존 `missing_shipping_versions`는
소스 태그가 있지만 배포 상태나 변경 설명을 확인하지 못한 목록이며, 실제 사용자 배포의 확정 목록이 아닙니다.
이 작업 파일은 저장소 밖에 유지합니다.

## 재확인과 보완 저장

매 새 수집 실행에서 공식 노트와 앱 스토어를 먼저 재확인합니다.
예정 시각 이후 첫 정기 수집에서 예외는 자동 만료됩니다. 새 공식 일정이 검증되지 않으면 계속 유예하지 않습니다.
HTTP 오류, 파싱 오류, 상충하는 버전은 원인과 출처를 남기고 다음 실행에서 다시 조사합니다.
기존 실행을 재개하면 고정된 캐시를 사용합니다. 새 게시·수정 내용을 확인하려면 새 실행 ID를 사용합니다.

공식 PR·커밋은 태그 포함 여부와 구체적인 동작을 함께 확인해 개별 보조 근거로 사용할 수 있습니다.
기능 플래그의 기본값, 대상 채널, 플랫폼, 단계적 배포 여부를 따로 확인합니다.
일부 PR을 확인했다고 버전 전체를 완료하거나 모든 코드 변경을 정식 출시 기능으로 집계하지 않습니다.
일반 오류 수정은 기존 기능 판정 규칙에 따라 제외합니다.

새 관측을 과거 수집 시각의 관측으로 표현하지 않습니다. 기존 완료본의 건수·근거·리비전을 보존합니다.
정책 개선만으로 과거 상태를 자동 재작성하지 않습니다. 보완 저장은 전체 필수 출처와 후보 판정 검증을 통과해야 합니다.

## 회귀 검증

미래 일정 허용, 예정 시각 만료, 조기 실제 배포 우선, 버전·제품 불일치, 마감 후 리비전,
일정 충돌·취소, 앱 스토어 장애, 원문 변조, 새 실행의 근거 복구를 검증합니다.
예정 버전이 기능 후보나 명시적 변경 없음 목록에 들어가지 않는지도 확인합니다.
