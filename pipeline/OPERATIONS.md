# 브라우저 기능 수집과 저장

Python 3.9 이상과 `schemas/requirements.txt`를 설치합니다. 브라우저별 조사 대상은 [공식 출처 설정](../config/sources.yml)에서 관리합니다.

1. 저장소 밖의 전용 작업 디렉터리에 업데이트 후보를 수집합니다. `--source`를 생략하면 실행 모드의 모든 활성 출처를 조사합니다. 일일 모드에서는 Brave, Vivaldi, Opera를 제외합니다.

   ```sh
   python -m pipeline.collect --private-dir "$PRIVATE_RUN" --source firefox-beta
   ```

2. 수집 에이전트가 `$PRIVATE_RUN/work/candidates/<source-id>.json`에 있는 항목을 [기능 기준](../docs/collection-policy.md)에 따라 분류합니다. 기능으로 확인한 항목만 아래 형식의 JSON 배열에 넣고 작업 디렉터리의 `features.json`으로 저장합니다. ID는 후보의 `source_item_id`와 마지막 `revisions` 항목의 `revision_id`를 사용합니다. 한 원문이 여러 기능을 설명하면 각 기능 키에 같은 출처 항목과 리비전을 지정합니다. 같은 기능을 다시 관찰하면 카탈로그에 있는 해당 브라우저의 `canonical_key`를 사용합니다.

   공개 미리보기(`evidence.excerpt`)가 220자이면 기능별로 `evidence_quote`를 지정합니다. 긴 항목은 비공개 후보의 `classification_text`에서 해당 기능을 설명하는 연속된 구절을 최대 1,200자까지 그대로 복사합니다. 더 짧은 항목은 인용을 생략하면 미리보기 전체를 사용합니다. 이전 실행의 후보에 긴 본문이 없으면 새 실행으로 다시 수집해 뒷부분을 인용합니다.

   ```json
   [
     {
       "source_item_id": "<source_item_id>",
       "revision_id": "<revision_id>",
       "canonical_key": "shared-tab-groups",
       "title": "탭 그룹 공유",
       "evidence_quote": "You can now share tab groups."
     }
   ]
   ```

3. 분류한 기능과 공식 근거를 저장합니다. 이 단계는 수집한 원문 버전으로 오프라인에서 실행됩니다. 빈 배열도 기존 카탈로그와 근거를 검증합니다. 참조가 끊어지면 후보를 보존하므로 근거를 복구한 뒤 다시 저장할 수 있습니다.

   ```sh
   python -m pipeline.collect --private-dir "$PRIVATE_RUN" --save-features "$PRIVATE_RUN/features.json"
   ```

수집 종료 코드 2는 요청한 출처 일부를 확인하지 못했다는 뜻입니다. 그 상태를 기능 변화 없음으로 해석하지 않습니다. 재시도할 때는 같은 디렉터리, `--resume`을 사용합니다. 원래 마감 시각과 출처를 재사용하며, 첫 실행에 제공한 메타데이터 입력도 다시 지정합니다. 실패한 출처의 기존 기능은 보존합니다.

## Edge 정책 상세 확인

분류 중 선택한 Edge 기능의 적용 조건이나 정확한 지원 플랫폼·버전을 확인해야 할 때만 해당 릴리스 항목이 직접 연결한 정책 상세 한 건을 읽습니다. 확인할 조건이 없으면 조회를 생략합니다. `edge-policies`는 이력 조회를 위해 등록 상태를 유지하며 `--source edge-policies`는 요청 전에 거부됩니다.

1. 분류 판정의 `source_item_id`와 `revision_id`를 후보 및 후보의 마지막 리비전과 대조합니다. 그 리비전의 `evidence.content_sha256`로 `$PRIVATE_RUN/work/browser/cache/<sha256>`를 찾고, 파일 바이트의 SHA-256을 다시 계산해 일치하는지 확인합니다. 일일·주간 실행의 `$PRIVATE_RUN`은 해당 실행 ID의 비공개 폴더입니다.
2. 검증한 PC·모바일 Stable·Beta 원문 또는 해당 릴리스 아카이브에서 후보의 `item_key`와 섹션, 후보 본문(`classification_text` 또는 `evidence.excerpt`)을 대조합니다. HTML ID가 없으면 파서가 만든 구역·태그·순번 키를 사용하고 섹션과 본문으로 행을 확인합니다. 같은 구절이 반복되어 해당 행을 하나로 특정하기 어렵다면 조회를 생략합니다. 확인한 행의 기능 설명에 있는 원래 `href`를 읽습니다. 다른 행이나 푸터의 링크, 정규화한 후보에서 사라진 링크는 제목이나 정책 이름으로 복원하지 않습니다.
3. 상대 `href`는 리비전의 공식 릴리스 URL(`evidence.url`)을 기준으로 해석합니다. 예를 들어 `https://learn.microsoft.com/en-us/deployedge/microsoft-edge-relnote-stable-channel`의 `microsoft-edge-policies/examplepolicy`는 `https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/examplepolicy`를 가리킵니다. 요청 전에 HTTPS, 정확한 호스트 `learn.microsoft.com`, 사용자 정보와 비표준 포트 없음, `/…/deployedge/microsoft-edge-policies/<정책 한 개>` 경로인지 확인합니다. 상세 경로를 먼저 확인한 뒤 쿼리와 프래그먼트를 제외하고 해당 페이지를 읽습니다. 정책 목록의 앵커라면 상세 URL로 바꾸지 않습니다. 이동을 자동으로 따르지 말고 목적지가 같은 정책의 상세 페이지인지 요청 전에 확인합니다. 목적지가 불분명하면 조회를 중단합니다. 정책 상세의 실제 페이지 제목이 선택한 기능의 정책과 맞는지 확인하고, 상세의 다른 링크는 따라가지 않습니다.
4. 실행 루트의 비공개 `edge-policy-evidence.md`에 후보 ID, 최신 리비전 ID, 원문 해시, 원래 href, 해석한 상세 URL, 관측 시각, 조건·플랫폼·버전 및 확인한 정책 구절을 남깁니다. 예를 들어 `src-… / sr-… / <sha256>`, `microsoft-edge-policies/examplepolicy` 및 위 상세 URL, 관측 시각, `Windows 140부터 적용`과 이를 뒷받침한 구절을 적습니다. 캐시가 없거나 해시, 행, 리비전, 공식 목적지 또는 지원 조건을 확인할 수 없으면 메모에 해당 조건을 미확인으로 표시합니다.
5. 공개 `evidence_quote`에는 릴리스 후보 본문의 구절만 사용합니다. 정책에서 확인한 별도 구절과 조건은 비공개 메모에 남기고, 릴리스 본문이 뒷받침하는 범위에서 저장합니다. 이 메모는 `features.json`이나 `classification.json` 옆에 두므로 `work/`가 정리된 뒤에도 남습니다. 분류 JSON 형식과 기존 정책 근거 참조는 그대로 사용합니다.

## 수집 기간과 재개

기존 `pipeline.run_daily` 호출은 일일 모드를 선택합니다. `--cutoff`에는 예정 시각과 시간대를 지정합니다. 일일 하한은 서울 시각으로 마감 30일 전 같은 시각입니다. 양끝을 포함합니다. `config/sources.yml`의 `baseline.daily_window_days`는 수집 기간입니다. `pipeline.collect`의 기본 모드는 수동입니다.

| 모드 | 범위 | 저장 |
| --- | --- | --- |
| `daily` | 최근 30일. Brave, Vivaldi, Opera를 제외한 활성 출처 | 기존 기능 분류 배열을 받습니다. `--daily-status`로 시작한 07:00 실행은 아래의 전수 판정 규칙을 사용합니다. |
| `weekly_reconcile` | 정책 시작일 00:00 KST부터 마감까지 | 모든 활성 출처와 후보의 최종 판정이 필요합니다. 결과는 비공개 실행 기록 및 검증된 기능과 근거에 저장합니다. |
| `manual` | 기본 최근 30일. `--source`와 `--since`로 대상과 하한 지정 | 별도 실행 ID와 분류 배열을 사용합니다. |
| `legacy` | 기존 정책 시작일부터 전체 수집 | 전환 전 수집 범위로 복귀할 때 사용합니다. 기본 분류 배열을 받습니다. |

주간 작업을 시험할 때는 새 ID와 주간 마감을 명시합니다. 아래 명령은 일회성 실행입니다.

```sh
python -m pipeline.run_daily --private-dir "$PRIVATE_STATE" --run-id "$WEEK_ID" \
  --mode weekly_reconcile --cutoff "$WEEK_CUTOFF"
python -m pipeline.run_daily --private-dir "$PRIVATE_STATE" --run-id "$WEEK_ID" \
  --save-features "$PRIVATE_STATE/$WEEK_ID/classification.json"
```

주간 분류 파일은 아래 일일 예시와 같은 `decisions`와 `dispositions` 배열을 사용합니다. 저장에는 모든 후보의 최종 판정이 필요합니다. `collection_complete`는 요청한 출처의 수집 결과입니다. 분류·저장까지 마치면 비공개 `feature-run.json`의 상태가 `saved`가 됩니다. 일부 출처만 진단한 주간 실행은 전체 대조로 저장할 수 없습니다. Brave, Vivaldi, Opera는 한국시간 일요일 10:00 주간 대조에서 수집합니다. 평일에 특정 출처를 확인할 때는 `--mode manual --source SOURCE_ID`를 지정합니다. `daily`에 주간 전용 출처를 지정하면 수집 전에 거부합니다. 기간이 30일 넘게 비면 주간 대조나 명시한 수동 기간으로 보충합니다. 과거 일일 상태의 날짜는 그대로 유지됩니다.

공식 시각은 시간대 오프셋을 적용합니다. 날짜만 있는 항목은 양쪽 경계일 전체를 포함하며 공개 근거에 일 단위 정밀도를 유지합니다. 날짜가 없으면 미상으로 유지합니다. 목록의 날짜는 상세의 정확한 시각과 다를 수 있어 경계 주변 상세를 읽습니다. 명시된 공식 수정일이 있으면 오래된 문서의 최근 변경도 확인합니다. 마감 이후 개정된 본문만 있으면 해당 출처는 미완료입니다. 과거 공개일만 알 수 있는 글은 주간 대조가 다시 확인합니다. 주간 발견 시점은 근거의 관측 시각에, 출처의 공식 날짜는 해당 날짜 필드에 기록됩니다.

비공개 실행 기록에 모드, 실행 ID, 코드·기준 커밋, 등록 설정과 보충 입력의 해시, 하한, 마감, 출처별 상태와 후보 파일 해시가 남습니다. 재개는 같은 입력만 허용합니다. 완료한 출처는 후보 파일의 해시를 확인합니다. 중단된 출처는 무결성을 확인한 응답으로 다시 파싱합니다. 가변 목록의 페이지 내용이 바뀌어 이어 읽을 수 없으면 새 ID로 다시 시작합니다. 이전 버전의 미완료 실행에는 새 검증 정보가 없으므로 새 ID로 수집합니다. 새 ID는 응답을 새로 가져옵니다.

출처별 `baseline.source_attempt_seconds`의 기본값은 900초입니다. 요청 사이와 항목 처리 중에 시간을 확인합니다. 진행 중인 HTTP 요청에는 기존 전송 시간 제한과 재시도 규칙이 적용됩니다. 한 출처에서 시간이나 페이지·문서 예산이 끝나면 나머지 출처를 조사합니다. 종료 코드 2이면 비공개 `source_results`의 오류와 남은 범위를 확인합니다. 프로세스를 강제 종료하면 상태가 `collecting`에 머물며 같은 마감으로 재개할 수 있습니다.

저장소 잠금은 수집 중에도 유지합니다. 겹치는 실행은 잠금 오류 후 같은 예정 시각으로 다시 시도합니다. 수집 후 다른 실행이 먼저 저장하면 저장기가 현재 근거와 카탈로그를 다시 읽습니다. 같은 리비전은 최초 저장된 관측을 유지합니다. 서로 다른 이력 또는 일일 상태용 기준 카탈로그가 충돌하면 새로 수집·분류합니다.

## 작업 공간과 일일 실행

각 수집에는 새 비공개 디렉터리를 지정합니다. 전체 후보와 응답 캐시는 분류하는 동안 `work/`에 머뭅니다. 분류 파일은 이 폴더 밖에 둡니다. 기능과 근거를 검증하고 저장하면 수집기가 자신의 `work/`를 정리합니다. 빈 선정 배열도 작업을 끝냅니다. 실행 상태 파일과 직접 만든 분류 파일은 남습니다. 부분 수집을 마감할 때는 저장 명령에 `--allow-partial`을 추가합니다. 실패한 저장에는 후보와 복구 자료가 남습니다.

일일 실행도 같은 경로를 사용합니다. 아래 예에서 후보는 `$PRIVATE_STATE/$RUN_ID/work/candidates/`에 있습니다.

```sh
python -m pipeline.run_daily --private-dir "$PRIVATE_STATE" --run-id "$RUN_ID"
python -m pipeline.run_daily --private-dir "$PRIVATE_STATE" --run-id "$RUN_ID" \
  --save-features "$PRIVATE_STATE/$RUN_ID/features.json"
```

이전 형식의 작업 디렉터리는 보존합니다. 이 명령으로 전환할 때는 새 실행 ID를 사용합니다. 기존 외부 스케줄러의 호출 인수는 운영 환경에서 맞춥니다. 저장 후에는 [저장소 PR 절차](../AGENTS.md)를 따릅니다.

ChromeStatus의 예전 출처에는 당시 출시 단계와 플랫폼별 지원 버전이 빠져 있습니다. 수집기는 기존 설명과 일치하는 항목의 첫 관측값을 비공개 비교 기준으로 보관합니다. 이때 공개 기능 이력은 그대로 유지합니다. 이후 공식 출시 단계 또는 데스크톱·Android·iOS·WebView 지원 버전이 바뀌면 해당 근거를 분류 후보로 전달합니다. 수정 시각만 바뀌면 건너뜁니다. 일일 실행에는 같은 체크아웃과 같은 `$PRIVATE_STATE`를 사용합니다. 비교 기준은 이 경로의 `.browser-benchmark-comparison-<uid>/`에 있으며 실행별 원문 정리 후에도 유지됩니다.


## 일일 수집 상태 파일

신규 스케줄 연동 시 수집 명령에 `--daily-status`와 한국시간 07:00:00 정각의 마감을 지정합니다. 같은 시점의 UTC 입력도 허용합니다. 공개 파일에는 한국 날짜와 `+09:00` 마감을 기록합니다. 동일 실행 재개에도 두 인수를 유지합니다. 아직 게시하지 않은 상태에서 이전 전체 출처 범위를 고정한 일이 있으면 새 일일 실행 ID로 시작합니다. 기본 수집 및 기존 수동·백필 실행은 상태 파일을 만들지 않습니다.

```sh
python -m pipeline.run_daily --private-dir "$PRIVATE_STATE" --run-id "$RUN_ID" \
  --cutoff "$CUTOFF" --daily-status
python -m pipeline.run_daily --private-dir "$PRIVATE_STATE" --run-id "$RUN_ID" \
  --save-features "$PRIVATE_STATE/$RUN_ID/features.json"
```

분류를 끝내고 회귀 및 저장 경로 검증을 통과한 뒤 저장합니다. 이 모드의 분류 항목에 `change_kind`를 지정합니다. 실제 기능 추가·변경에는 `product_change`를 쓰고, 기능이 동일한 기존 항목의 공식 근거만 보강할 때는 `evidence_only`를 씁니다. 소스 본문이나 링크 변경만으로는 기능 변경이 아닙니다. 최상위 `collected_feature_count`는 이 실행에서 채택한 고유 기능 수입니다. 기능마다 한 번만 세며, 근거 보강만 한 기능도 포함합니다. 제외·미변경으로 판정한 후보는 세지 않습니다. `change_count`는 그중 실제 기능 추가·변경 수입니다.

이 모드의 비공개 분류 파일은 `decisions`와 `dispositions` 배열을 갖는 객체입니다. `decisions`에는 위 기능 분류와 `change_kind`를 사용합니다. `dispositions`에는 각 후보의 `source_id`, `source_item_id`, 최신 `revision_id`, `disposition`을 한 번씩 기록합니다. 결과는 `selected`, `excluded`, `unchanged` 중 하나입니다. `selected`인 후보만 기능 분류 행과 연결됩니다. 판정이 없거나 미해결인 후보가 하나라도 있으면 완료로 저장하지 않습니다. 후보가 있지만 모두 제외하면 `decisions`만 빈 배열입니다. 두 배열이 모두 비는 경우는 후보가 없는 날뿐입니다. 일반 수집의 기존 배열 형식은 그대로입니다.

브라우저별 저장을 사용하지 않고 일일 전체 검증을 마치지 못했으면 `--save-features` 대신 같은 실행에 `--record-incomplete`를 사용합니다. 이 단계는 두 건수를 `null`로 기록하고 후보를 보존합니다. `--allow-partial`로 완료 상태를 쓸 수 없습니다. 같은 날짜의 완료 상태는 미완료 재시도로 후퇴하지 않습니다. 완료본이 있으면 같은 날짜의 재실행은 기능 변경이나 건수 변경을 덮어쓰지 않습니다.

기존 08:00 공개 파일은 CI와 소비자가 계속 읽습니다. 날짜별 파일은 하나이며, 기존 파일이 미완료여도 다른 마감으로 대체할 수 없습니다. 아직 게시하지 않은 08:00 실행은 새 코드로 재개하거나 저장할 수 없습니다. 07:00 수집에는 새 실행 ID를 사용합니다. 이미 게시한 08:00 실행은 같은 분류로 저장을 재시도해 비공개 정리를 마칠 수 있습니다.

변경이 있는 완료 상태는 기능·근거와 같은 작업 트리 트랜잭션에 저장됩니다. GitHub에는 같은 PR에 올립니다. 새 기능·근거 파일이 없으면 상태 파일만 올립니다. 진단 로그는 공개하지 않습니다. CI는 `python -m pipeline.daily_status`로 상태 파일을 검증합니다.


### 브라우저별 저장과 재시도

일일 상태 실행이나 주간 전체 대조에서는 검증을 마친 브라우저부터 저장할 수 있습니다.
예를 들어 Firefox의 모든 필수 출처가 같은 마감으로 수집되면, Firefox 후보만 담은 분류 파일을 준비합니다.
각 후보의 최종 판정과 채택한 기능의 `change_kind`는 위 일일 형식과 같습니다.

```sh
python -m pipeline.run_daily --private-dir "$PRIVATE_STATE" --run-id "$RUN_ID" \
  --save-browser firefox --save-features "$PRIVATE_STATE/$RUN_ID/firefox.json"
```

출처를 지정한 실행도 해당 브라우저의 필수 출처를 모두 확인해야 합니다.
각 저장은 전체 근거 그래프를 검증하고 기능, 근거, 브라우저별 결과 및 일일 상태를 함께 기록합니다.
`data/browser-status/<mode>/<UTC 시각>.json`의 `scope.expected`가 마감 시점의 필수 출처입니다.
`browsers`의 완료 항목에는 고유 기능 수, 분류 체크섬, 선택한 기능·근거 리비전의 확인 정보가 있습니다.
미완료 브라우저의 두 건수는 `null`입니다. 일일 전체 파일의 건수는 마지막 브라우저까지 완료됐을 때 확정합니다.
주간 대조의 브라우저별 저장은 주간 결과만 기록합니다.

다른 브라우저의 후보와 체크포인트는 비공개 실행 폴더에 남습니다.
같은 실행에서 수집을 재개하거나 다음 브라우저를 저장할 수 있습니다. 이미 저장한 브라우저는 같은 분류로 재시도할 수 있습니다.
첫 브라우저별 저장 이후에는 남은 브라우저도 `--save-browser`로 마칩니다.
공개 결과를 Git에 커밋했거나 다른 실행에서 근거가 변경됐다면 같은 마감, 새 실행 ID로 다시 수집합니다.
필수 출처·등록소·수집 구간이 일치하고 기존 기능과 인용 근거가 그대로 연결되는지 확인한 뒤 남은 브라우저를 저장합니다.
이 과정은 먼저 공개한 브라우저의 원래 건수를 유지합니다.
모든 브라우저가 완료되고 저장 트랜잭션이 성공했음을 확인한 후 해당 실행의 비공개 후보를 정리할 수 있습니다.
실패한 저장의 복구 저널이 남아 있으면 해당 실행을 보존하고 다음 저장에서 복구를 먼저 마칩니다.

같은 리비전의 공개 인용문이 브라우저별 결과에 고정되면 이후 수동·주간·일일 저장도 그 인용문을 보존합니다.
CI는 PR의 기준 커밋 또는 push 직전 커밋과 비교해 확정한 결과의 삭제·수정을 검사합니다.
신규 결과의 필수 출처는 Git에 올리는 현재 등록소의 해시와 일치해야 합니다.
이전 비교 기준 커밋에 이미 있던 동일한 결과는 등록소가 이후 바뀌어도 읽을 수 있습니다.

일일 전역 저장과 주간 전체 저장도 수집 시 고정한 출처별 체크포인트와 후보 파일을 대조합니다.
고정 정보가 유실된 경우에는 같은 마감으로 새 실행을 시작합니다. 이전 형식의 비공개 실행은
로컬 Git에서 당시 수집기 커밋과 기존 범위를 확인할 수 있을 때 기존 전역 저장 경로로 마칠 수 있습니다.
브라우저별 확정 근거의 인용문은 기능에 지정한 문구를 우선하고, 생략하면 연결된 출처 리비전의 발췌문을 사용합니다.


### 주간 마감과 이전 형식 처리

전체 주간 저장이 끝나면 `data/weekly-status/YYYY-MM-DDTHHMMSS.ffffffZ.json`을 기능·근거와 같은 트랜잭션에서 기록합니다.
파일명은 UTC이며, 같은 시각을 다른 시간대로 입력해도 같은 파일을 사용합니다.
`scope`는 전체 활성 출처와 역사 구간을 고정하고, `classification`은 비공개 최종 분류의 SHA-256입니다.
전환 마감부터 `feature_ids`와 `collected_feature_count`에는 근거 보강을 포함한 고유 채택 기능 목록과 수를 기록합니다.
여러 근거가 같은 기능을 지지하면 한 번만 셉니다. 확인된 0건도 파일을 작성합니다.
주간 전역 분류에서 `change_kind`는 기존처럼 선택 사항이며 이 파일에는 제품 변경 수를 기록하지 않습니다.

전체 저장이 먼저 끝난 마감에서는 같은 실행 ID와 같은 분류로 재시도해 정리를 끝낼 수 있습니다.
새 실행 ID의 전역 또는 브라우저별 재저장은 거부합니다.
브라우저별 결과가 먼저 있으면 그 마감은 계속 `--save-browser`로 마칩니다.
기존 브라우저별 v1 파일과 전역 주간 파일은 서로 다른 소비 경로입니다.

첫 전환 마감은 **2026년 11월 29일 일요일 10:00 한국시간**(01:00 UTC)입니다.
그 이전 마감에 확정한 v1 브라우저별 결과가 있으면 원래 결과를 검증하고 이어갈 수 있습니다.
이전 마감에 기록이 없으면 브라우저별 신규 저장을 차단합니다.
이전 마감의 검증된 전역 실행은 기존 분류 형식으로 끝낼 수 있으며, 원래 총계를 재구성할 수 없어 `feature_ids`와 `collected_feature_count`가 모두 `null`입니다.
이미 완료한 이전 실행의 비공개 상태와 같은 분류가 남아 있으면 원래 실행 ID로 완료 확인을 재시도할 수 있습니다.

최초 기록을 쓰기 전에 같은 cutoff와 같은 역사 구간이 기존 기능 또는 근거에 있으면 저장을 중단합니다.
이 자료만으로는 당시 전체 주간 실행인지 수동 확인인지, 어떤 후보를 채택했는지 구별할 수 없습니다.
이전 코드의 0건 전역 저장은 공개 파일이나 Git 변경을 하나도 남기지 않을 수 있습니다. 확인된 기존 결과가 없으면 이 경우와 미실행을 구별할 수 없습니다.
현재 시각이나 Git 커밋 시각으로 과거 결과를 추정하지 않습니다.
배포 전에 11월 29일 마감부터 모든 주간 저장이 새 코드를 사용할 수 있는지 확인합니다.
구형 writer가 그 이후 마감을 처리할 수 있다면 첫 배포와 최초 새 기록 이전에 전환 마감을 실제 첫 보호 대상 주간으로 늦춰야 합니다.

전환 마감부터 전역 주간 저장도 수집 시점의 코드·데이터 Git 커밋, 등록소, 카탈로그와 모든 필수 근거 파일의 해시를 저장 직전까지 확인합니다.
분류 대기 중 다른 수집이 자료를 변경했으면 같은 마감으로 새 실행을 수집하고 분류합니다.
Git이 없는 데이터 폴더에서도 수집 때 기록한 파일 해시를 검사합니다.
이 기준을 남기지 않은 이전 형식의 비공개 실행으로는 전환 이후의 새 전역 건수를 확정할 수 없습니다.
